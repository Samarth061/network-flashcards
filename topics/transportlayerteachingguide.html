Section 1

Introduction & Transport-Layer Services

What the transport layer does, how it relates to the network layer, and the two Internet transport protocols.

Imagine two people in different cities trying to have a conversation. The postal system delivers envelopes from house to house—but it doesn't know or care which person in the house the letter is addressed to. Someone inside each house reads the name on the letter and hands it to the right person. The transport layer is exactly that someone inside the house.

Core Definition: A transport-layer protocol provides logical communication between application processes running on different hosts. The network layer provides logical communication between hosts; the transport layer extends this to process-to-process delivery.

3.1.1 Transport Layer vs. Network Layer

The distinction between these two layers is subtle but critical:

Household Analogy — Transport vs. Network Layer
Analogy ElementNetwork Concept
Letters in envelopesApplication messages
Cousins (individual people)Processes
HousesHosts (end systems)
Ann and Bill (in-house distributors)Transport-layer protocol
Postal service (house-to-house)Network-layer protocol (IP)

Key Constraint: The services a transport protocol can provide are constrained by the underlying network-layer service model. If IP cannot guarantee delay or bandwidth, TCP/UDP cannot either — at least not without adding mechanisms on top.

3.1.2 Internet Transport Protocols: TCP and UDP

IP — the Internet's network layer protocol — provides a best-effort delivery service: no guarantees on delivery, ordering, or data integrity. It is an unreliable service. Both TCP and UDP sit on top of IP and extend it in different ways.

UDP — User Datagram Protocol

  • Connectionless (no handshaking)
  • Unreliable — no guarantee of delivery or ordering
  • Provides only multiplexing/demultiplexing + error checking
  • Low overhead (8-byte header)
  • Used by: DNS, SNMP, RIP, streaming media

TCP — Transmission Control Protocol

  • Connection-oriented (3-way handshake)
  • Reliable, in-order byte stream delivery
  • Flow control (receiver buffer management)
  • Congestion control (network protection)
  • Used by: HTTP, SMTP, FTP, Telnet

Terminology Note: The book refers to both TCP and UDP packets as segments. The term datagram is reserved for network-layer (IP) packets. In RFCs, UDP packets are sometimes called datagrams, but Kurose & Ross use "segment" throughout for clarity.

Section 2

Multiplexing & Demultiplexing

How one transport layer serves many application processes simultaneously using port numbers.

At any moment, a computer may run a web browser, an email client, a file-transfer session, and more — all simultaneously receiving data from the network. The transport layer needs a way to hand incoming data to the correct application. This is demultiplexing. The reverse — collecting data from multiple apps and sending them as segments — is multiplexing.

Port Numbers: Each segment carries a source port number and a destination port number, each 16 bits (range: 0–65535). Port numbers 0–1023 are well-known ports reserved for standard protocols (HTTP=80, FTP=21). Applications above 1023 are assigned dynamically.

Transport-Layer Multiplexing and Demultiplexing

Connectionless Demultiplexing (UDP)

A UDP socket is identified by a two-tuple: (destination IP address, destination port number). Two UDP segments with different source addresses/ports but the same destination IP and destination port will be directed to the same socket.

Why does the source port matter in UDP? It serves as a "return address." When Host B wants to reply to Host A, B uses A's source port number as the destination port in its response segment.

Connection-Oriented Demultiplexing (TCP)

A TCP socket is identified by a four-tuple: (source IP, source port, destination IP, destination port). This means two TCP segments arriving with different source IPs or source ports — even with the same destination port 80 — are directed to different sockets.

TCP Demultiplexing — Multiple Clients, Same Destination Port

UDP socket = 2-tuple (dst IP, dst port). TCP socket = 4-tuple (src IP, src port, dst IP, dst port). This is why a web server can handle thousands of simultaneous HTTP connections all arriving on port 80 — each is a unique 4-tuple.

Section 3

Connectionless Transport: UDP

The minimal transport protocol — what it does, why you'd use it, and how its checksum works.

UDP does almost nothing on top of IP. It adds port numbers for multiplexing, a length field, and a checksum — that's it. There is no handshaking, no connection state, no congestion control, and no reliability. If the application passes data to UDP, UDP immediately shoots it out as a segment without consulting the other end.

Why Use UDP Instead of TCP?

  • Finer application control over what/when to send — UDP doesn't throttle; TCP's congestion control can delay or reduce transmission.
  • No connection-establishment delay — DNS uses UDP precisely because a TCP 3-way handshake would roughly double DNS query latency.
  • No connection state — A UDP server can support far more simultaneous clients because it maintains no per-connection buffers or variables.
  • Small header overhead — UDP has 8 bytes; TCP has 20 bytes.
ApplicationProtocolReason
DNSUDPNo setup delay; retransmit at app level if needed
SNMP (network mgmt)UDPMust work under congestion; TCP may not be available
RIP routing updatesUDPPeriodic — stale updates replaced by newer ones
Streaming mediaUDP or TCPTolerates loss; avoids TCP congestion throttling
HTTP, SMTP, FTPTCPRequires reliable delivery

UDP and Congestion: UDP has no congestion control. If all applications used UDP freely during network congestion, router queues would overflow and TCP connections (which do back off) would be crowded out. This is a real fairness concern.

3.3.1 UDP Segment Structure

The UDP header is only 8 bytes — four fields, two bytes each:

Source Port 16 bits Port number of the sending process. Used as return address in replies.
Destination Port 16 bits Port number of the receiving process. Used by transport layer to demultiplex to the correct socket.
Length 16 bits Total length of the UDP segment (header + data) in bytes. Minimum value is 8 (header only).
Checksum 16 bits 1s complement of sum of all 16-bit words in segment. Used for error detection. All-zeros means no checksum was computed.

3.3.2 UDP Checksum — Worked Example

The sender adds up all 16-bit words in the segment, wraps overflows around, then takes the 1s complement. The receiver adds all four 16-bit words (including checksum) — if the result is all 1s, no error was detected.

1s Complement Checksum Calculation

At the receiver, all four 16-bit words (including the checksum) are summed. If no errors occurred, the result is 1111111111111111. If any bit is 0, an error has been detected.

End-End Principle: UDP provides checksum even though link-layer protocols (like Ethernet) also check for errors. Why? Because not all links provide error checking, and errors can occur in router memory. Reliable end-to-end integrity requires an end-to-end check — the "end-end principle."

Section 4

Principles of Reliable Data Transfer

Building rdt1.0 through rdt3.0 — how to achieve reliability over an unreliable channel.

Here we build up a reliable data transfer (rdt) protocol step by step, each version handling a harder channel model. The goal: the service abstraction is a perfectly reliable channel; the reality is a channel that can corrupt bits or lose packets entirely.

Interface: rdt_send(data) — called from above to send data. udt_send(packet) — sends over unreliable channel. rdt_rcv(packet) — called when packet arrives. deliver_data(data) — delivers to upper layer.

rdt1.0 — Perfectly Reliable Channel

If the channel never corrupts or loses packets, the protocol is trivial: sender wraps data in a packet and sends it; receiver extracts and delivers. No feedback needed.

rdt1.0 FSM — Sender and Receiver

rdt2.0 — Channel with Bit Errors (ACK/NAK)

Now bits can be flipped. The receiver must detect corruption and tell the sender. This introduces ARQ (Automatic Repeat reQuest) — three new mechanisms:

1
Error Detection

A checksum field in the data packet lets the receiver detect bit errors.

2
Receiver Feedback

The receiver sends explicit ACK (positive) or NAK (negative) acknowledgments back to the sender.

3
Retransmission

On receiving a NAK, the sender retransmits the corrupted packet. This makes rdt2.0 a stop-and-wait protocol.

Fatal Flaw in rdt2.0: What if the ACK or NAK itself is corrupted? The sender can't tell if the receiver got the packet. If the sender re-sends on a garbled ACK/NAK, the receiver can't tell if it's new data or a retransmission. rdt2.0 is broken.

rdt2.1 — Sequence Numbers Fix Duplicates

The fix: add a sequence number to each data packet. For stop-and-wait, a 1-bit sequence number suffices — it alternates between 0 and 1. The receiver uses it to distinguish retransmissions from new data.

Sender Behavior (rdt2.1)

  • Numbers packets 0 or 1
  • Waits for ACK or NAK
  • On NAK or corrupted ACK/NAK: retransmits same packet
  • On correct ACK: moves to next sequence number

Receiver Behavior (rdt2.1)

  • Checks seq number against expected
  • Correct packet, correct seq: deliver + ACK
  • Correct packet, wrong seq: must be duplicate, ACK (don't deliver)
  • Corrupted packet: send NAK

rdt2.2 — NAK-Free Protocol

Instead of sending a NAK, the receiver can send an ACK for the last correctly received packet. A duplicate ACK for sequence 0 means sequence 1 was corrupt — same effect as NAK. The sender checks the ACK's sequence number field.

Insight: rdt2.2 is NAK-free by using duplicate ACKs instead of explicit NAKs. TCP uses this exact approach — no NAK packets, but duplicate ACKs trigger retransmission.

rdt3.0 — Lossy Channel with Bit Errors (Timers)

Now packets can be lost entirely (not just corrupted). A lost data packet or lost ACK leaves the sender waiting forever. Solution: a countdown timer. If the sender doesn't hear an ACK within a timeout interval, it retransmits.

rdt3.0 Operation — Four Scenarios

rdt3.0 = Alternating-Bit Protocol. Sequence numbers alternate 0 ↔ 1. Sender starts timer on every packet; retransmits on timeout. Sequence numbers handle duplicates. This protocol is correct but slow — it's stop-and-wait with 1 packet in flight at a time.

Performance of rdt3.0 (Stop-and-Wait)

Consider two hosts on opposite coasts: RTT = 30 ms, link rate R = 1 Gbps, packet size L = 1,000 bytes (8,000 bits).

// Transmission time to send one packet: d_trans = L / R = 8000 bits / 10^9 bits/sec = 8 microseconds // Sender utilization (fraction of time actually sending): U_sender = (L/R) / (RTT + L/R) = 0.008 ms / (30.008 ms) = 0.00027 // Only 0.027% of the time! // Effective throughput (despite 1 Gbps link): Throughput ≈ L / (RTT + L/R) = 8000 bits / 0.030008 s ≈ 267 kbps

Critical Performance Problem: Stop-and-wait achieves only 267 kbps on a 1 Gbps link. The sender is idle 99.97% of the time. Solution: pipelining — allow multiple packets to be in flight simultaneously.

Section 5

Pipelined Protocols: Go-Back-N & Selective Repeat

How to keep the pipe full — window-based protocols and their error recovery strategies.

Pipelining allows the sender to send multiple packets without waiting for each individual ACK. The sender can have up to N unacknowledged packets in the pipeline at once (the window size). Two protocols handle errors differently when they occur.

3.4.3 Go-Back-N (GBN)

The sender maintains a window of size N. On timeout or wrong-seq-num ACK, it retransmits the lost packet and all subsequent packets — it goes back to N.

GBN Sender Window — Sequence Number Space

GBN Cumulative ACKs: An ACK for packet n means all packets up through n have been received. The receiver discards all out-of-order packets — no buffering needed. On timeout, the sender resends ALL unACK'd packets (base through nextseqnum-1).

// GBN Sender — three events: Event: rdt_send(data) if (nextseqnum < base + N) { send packet[nextseqnum]; if (base==nextseqnum) start_timer; nextseqnum++; } else refuse_data(data) Event: timeout start_timer; resend ALL of sndpkt[base..nextseqnum-1] Event: ACK(n) received base = n + 1 if (base == nextseqnum) stop_timer; else start_timer

3.4.4 Selective Repeat (SR)

GBN wastes bandwidth retransmitting good packets. SR retransmits only the packet(s) suspected lost. The receiver buffers out-of-order packets. Each packet has its own timer.

SR Sender and Receiver Windows — Note They Can Differ

SR Window Size Constraint: The SR receiver window must be ≤ half the sequence number space. If window size W > (max_seq + 1) / 2, the receiver can't distinguish a retransmitted old packet from a new one in a wrapped-around sequence space. For GBN, window must be ≤ (max_seq + 1 - 1) = max_seq.

Section 6

TCP: Connection & Segment Structure

TCP's byte-stream model, the 20-byte header anatomy, and how sequence/ACK numbers work.

TCP is connection-oriented: before data flows, a 3-way handshake establishes the connection and initializes state variables at both ends. TCP is also full-duplex (data flows both ways simultaneously) and always point-to-point (one sender, one receiver — no multicast).

TCP is NOT a circuit: The "connection" exists only in the end systems (buffers, state variables). Routers in between are completely oblivious — they only see IP datagrams, never TCP connections.

3.5.1 The TCP Connection — Buffers and MSS

When a connection is established, both sides allocate send buffers and receive buffers. TCP sends data when it has enough to fill a segment, or when forced by a timer or PSH flag. The Maximum Segment Size (MSS) is the maximum application data per segment — typically 1,460 bytes (to fit within a 1,500-byte Ethernet frame with 40 bytes of TCP/IP headers).

3.5.2 TCP Segment Structure

The TCP header is 20 bytes long (when no options are present). Here is every field:

TCP Segment Header Format (20 bytes minimum)
Source/Dest Port 16 bits Multiplexing/demultiplexing — identifies sending and receiving process sockets.
Sequence Number 32 bits Byte-stream position of the first data byte in this segment (not packet number). Random initial value chosen at connection setup.
Acknowledgment Number 32 bits Next byte the sender is expecting from the other side. Cumulative — implicitly ACKs all bytes below this number.
Header Length 4 bits Length of TCP header in 32-bit words. Needed because Options field is variable-length. Typical value: 5 (= 20 bytes).
Flags (ACK/RST/SYN/FIN/PSH/URG) 6 bits ACK: ACK field is valid. SYN: connection setup. FIN: connection teardown. RST: reset. PSH: push to app now. URG: urgent data present.
Receive Window (rwnd) 16 bits Flow control — number of bytes the receiver is currently willing to accept. Tells the sender how much data it can send without overflow.
Checksum 16 bits Same 1s complement checksum as UDP. Mandatory in TCP (unlike UDP where it's optional in IPv4).

Sequence Numbers and Acknowledgment Numbers

TCP views data as a byte stream. Sequence numbers count bytes, not packets. The seq number of a segment = byte-stream position of the first byte in that segment.

Example: A 500,000-byte file with MSS = 1,000 bytes produces 500 segments. First segment: seq = 0. Second: seq = 1,000. Third: seq = 2,000. And so on. The seq field tells the receiver exactly where each chunk fits in the reassembled stream.

ACK number = next expected byte. If Host A has received all bytes 0–535, its ACK number is 536. TCP is said to use cumulative acknowledgments — ACK(536) implicitly acknowledges all bytes 0–535.

Suppose Host A (client, starts at seq 42) opens a Telnet session to Host B (server, starts at seq 79). The user types 'C':

Section 7

TCP: Reliable Data Transfer

RTT estimation, retransmission timeout, fast retransmit, and how TCP handles loss scenarios.

3.5.3 RTT Estimation and Timeout

TCP needs a timeout interval that is large enough to avoid unnecessary retransmissions, but small enough to recover quickly from loss. It estimates the RTT dynamically using an exponentially-weighted moving average (EWMA).

// Estimated RTT (EWMA with α = 0.125): EstimatedRTT = (1 - α) · EstimatedRTT + α · SampleRTT = 0.875 · EstimatedRTT + 0.125 · SampleRTT // DevRTT — RTT variation (β = 0.25): DevRTT = (1 - β) · DevRTT + β · |SampleRTT - EstimatedRTT| = 0.75 · DevRTT + 0.25 · |SampleRTT - EstimatedRTT| // Timeout interval (add margin for variance): TimeoutInterval = EstimatedRTT + 4 · DevRTT

Why EWMA? Recent samples should count more than old ones (network conditions change). The exponential weighting does this automatically — the weight of a SampleRTT decays exponentially as new samples arrive. The larger α = 0.125 gives more weight to new samples; smaller means smoother but slower adaptation.

Karn's Algorithm: TCP never measures SampleRTT for a retransmitted segment. Why? After a retransmission, we can't tell if an arriving ACK is for the original or the retransmission — either would give a garbage RTT estimate. Also: when a timeout occurs, the timeout interval is doubled (exponential backoff) to avoid flooding a congested network.

3.5.4 Reliable Data Transfer

TCP maintains SendBase (oldest unACK'd byte) and NextSeqNum (next byte to send). It uses a single retransmission timer for the oldest unACK'd segment.

/* Simplified TCP Sender */ NextSeqNum = InitialSeqNum; SendBase = InitialSeqNum; Event: data from app create segment with seq = NextSeqNum if timer not running: start_timer pass to IP; NextSeqNum += length(data) Event: timer timeout retransmit segment with smallest seq number start_timer // restart Event: ACK(y) received if (y > SendBase): SendBase = y if (unACK'd segments exist): start_timer

Three Interesting TCP Retransmission Scenarios

Scenario 1: Lost ACK

Host A sends seq=92 (8 bytes). ACK=100 is lost. Timer expires. A retransmits seq=92. B receives duplicate, discards bytes (but sends ACK=100 again). A receives ACK=100, moves on.

Scenario 2: Cumulative ACK Saves Retransmission

A sends seq=92 and seq=100. Both arrive at B. ACK=100 is lost, but ACK=120 arrives before timeout. A knows B has everything up to 119 — no retransmission needed! Cumulative ACKs save work.

Fast Retransmit

Waiting for a timeout can take hundreds of milliseconds. TCP detects likely loss earlier through duplicate ACKs: when the receiver gets an out-of-order segment, it resends the ACK for the last in-order byte received.

TCP Receiver EventACK Action
In-order segment, all prev ACK'dWait up to 500ms for next in-order; then send ACK
In-order, one segment waitingSend single cumulative ACK immediately
Out-of-order segment (gap detected)Send duplicate ACK immediately (gap start)
Segment fills a gapSend ACK immediately if gap start filled

Fast Retransmit Rule: If the sender receives 3 duplicate ACKs for the same sequence number, it retransmits the missing segment immediately — before its timer expires. Three duplicates strongly suggests the segment was lost (not just reordered).

// Fast Retransmit addition to ACK handler: Event: ACK(y) received if (y > SendBase): SendBase = y; dupACKcount = 0 if (unACK'd exist): start_timer else: // duplicate ACK dupACKcount++ if (dupACKcount == 3): resend segment with seq = y // fast retransmit!

TCP: GBN or SR? TCP is a hybrid. Like GBN it uses cumulative ACKs and a single timer. Like SR, modern implementations buffer out-of-order segments and use selective acknowledgment (SACK, RFC 2018). In practice, TCP typically retransmits at most one segment per event (more SR-like), not all unACK'd packets like GBN.

Section 8

TCP: Flow Control

How the receiver prevents the sender from overwhelming its buffer using the receive window.

Even if the network is perfect, the sender could overrun the receiver's application buffer if the application reads data slowly. Flow control is a speed-matching service between sender and receiver (distinct from congestion control, which matches sender to network capacity).

Key Variables at Receiver B: RcvBuffer = total receive buffer size. LastByteRcvd = last byte arrived from network. LastByteRead = last byte read by application. The constraint: LastByteRcvd − LastByteRead ≤ RcvBuffer.

TCP Receive Buffer and the rwnd Field

The receiver puts its current rwnd value in the receive window field of every TCP segment it sends. The sender ensures its amount of unACK'd data never exceeds rwnd.

The rwnd=0 Problem: Suppose B's buffer fills up (rwnd=0) and it has nothing to send A. A stops sending. Later, B's app reads data — but B doesn't tell A! A is stuck forever. Solution: when rwnd=0, A continues sending 1-byte "probe" segments. When B replies with a nonzero rwnd, the deadlock breaks.

Flow Control vs. Congestion Control

Both throttle the sender, but for different reasons:

  • Flow control: prevents receiver buffer overflow
  • Congestion control: prevents network router overflow

The effective send rate is limited by: min(cwnd, rwnd) / RTT

UDP Has No Flow Control

UDP appends segments to a finite socket buffer. If the application reads too slowly, the buffer overflows and segments are silently dropped. Applications using UDP must manage their own rate.

Section 9

TCP: Connection Management

The 3-way handshake, connection teardown with FIN/ACK, TCP state machines, and the SYN flood attack.

3.5.6 Establishing a TCP Connection: 3-Way Handshake

1
SYN — Client sends connection request

SYN bit = 1, seq = client_isn (randomly chosen). No data payload. This is the "SYN segment."

2
SYNACK — Server grants connection

SYN bit = 1, ACK bit = 1. seq = server_isn (server's random ISN). ACK = client_isn + 1. Server allocates buffers and variables. Called a "SYNACK segment."

3
ACK — Client confirms

SYN bit = 0, ACK bit = 1. ACK = server_isn + 1. Client allocates buffers. May carry data in payload. Connection is now established.

TCP 3-Way Handshake

Closing a TCP Connection: Four-Way FIN Handshake

Either side can initiate closure. The closing side sends a FIN segment; the other side ACKs it; then that side sends its own FIN; the first side ACKs it. This results in four segments total (though the middle ACK and FIN are often combined into one).

TIME_WAIT State: After sending the final ACK, the client waits in TIME_WAIT (typically 30 sec–2 min) before releasing the port. This ensures the final ACK was received — if not, the server will retransmit its FIN, giving the client a chance to re-ACK.

TCP State Machines

Client States (Typical)

CLOSED → send SYN → SYN_SENT → receive SYNACK, send ACK → ESTABLISHED → send FIN → FIN_WAIT_1 → receive ACK → FIN_WAIT_2 → receive FIN, send ACK → TIME_WAIT → (wait) → CLOSED

Server States (Typical)

CLOSED → LISTEN → receive SYN, send SYNACK → SYN_RCVD → receive ACK → ESTABLISHED → receive FIN, send ACK → CLOSE_WAIT → send FIN → LAST_ACK → receive ACK → CLOSED

Security: The SYN Flood Attack

Because the server allocates buffers and state upon receiving a SYN (before completing the 3-way handshake), an attacker can exhaust server resources by sending thousands of SYN segments without ever completing the handshake.

SYN Flood Defense — SYN Cookies (RFC 4987): Instead of allocating state, the server encodes connection info into a carefully crafted initial sequence number (a hash of src/dst IPs and ports + a secret). State is only allocated when a valid ACK arrives — the server reconstructs state from the "cookie" in the ACK's acknowledgment field.

Section 10

Principles of Congestion Control

What causes congestion, its costs to network performance, and the two broad approaches to controlling it.

Packet retransmission treats the symptom of congestion (a lost segment) but not the cause (too many senders, too fast). Congestion control mechanisms throttle senders to prevent or react to overload in the network.

3.6.1 The Costs of Congestion — Three Scenarios

Scenario 1: Two senders, infinite buffers. As sending rate approaches R/2, queuing delays grow without bound. Throughput caps at R/2 but delay becomes infinite. Lesson: large queuing delays occur near link capacity.

Scenario 2: Finite buffers, reliable transport. Senders must retransmit lost packets. This wasted work means at offered load R/2, actual delivered throughput is only R/3. Premature timeouts waste even more bandwidth on duplicate transmissions. Lesson: retransmissions consume bandwidth; throughput efficiency degrades.

Scenario 3: Multihop paths, finite buffers. When a packet is dropped at the second hop after already traversing the first hop, all the first-hop bandwidth used to forward that packet is wasted. Throughput collapses to zero as load increases. Lesson: upstream capacity wasted on packets eventually dropped downstream.

Congestion Cost Summary — Throughput vs. Offered Load

3.6.2 Approaches to Congestion Control

ApproachDescriptionExample
End-to-end congestion controlNo explicit network feedback. End systems infer congestion from packet loss and delay. TCP uses this.TCP (loss events = timeout or 3 dup ACKs)
Network-assisted congestion controlRouters provide explicit feedback to senders via single-bit flags or explicit rate signals in packets.ATM ABR, DECnet, ECN (TCP/IP extension)

ATM ABR Congestion Control (brief): Uses Resource Management (RM) cells interspersed with data cells. Switches set EFCI bit (mild congestion), CI/NI bits (severe), or ER field (explicit rate) in RM cells to directly signal rate adjustments to sources. More fine-grained than TCP's binary loss-based signal.

Section 11

TCP Congestion Control

Slow start, congestion avoidance, fast recovery, and the cwnd/ssthresh state machine.

TCP must use end-to-end congestion control (IP provides no congestion signals). The core mechanism: the sender maintains a congestion window (cwnd) that limits how much unACK'd data can be in the network at once. The effective send rate is approximately min(cwnd, rwnd) / RTT.

Loss Event Detection: TCP treats two events as evidence of congestion: (1) a timeout — strong signal, network probably severely congested; (2) 3 duplicate ACKs — weaker signal, likely a single lost packet but network still delivering.

3.7 The Three Components of TCP Congestion Control

1. Slow Start

When a new connection starts (or after a timeout), cwnd begins at 1 MSS and doubles every RTT: for every ACK received, cwnd increases by 1 MSS. Despite its name, slow start is exponential growth.

Slow Start — Exponential cwnd Growth

Slow start ends when:

  • cwnd reaches ssthresh (slow start threshold) → transition to Congestion Avoidance
  • A timeout occurs → ssthresh = cwnd/2, cwnd = 1, restart slow start
  • 3 duplicate ACKs → fast retransmit, enter Fast Recovery

2. Congestion Avoidance

Once cwnd ≥ ssthresh, growth slows to linear: +1 MSS per RTT (approximately +MSS × MSS/cwnd per ACK received). The sender is "close to the edge" so it probes cautiously.

Congestion avoidance ends when:

  • Timeout → ssthresh = cwnd/2, cwnd = 1, restart slow start
  • 3 duplicate ACKs → ssthresh = cwnd/2, cwnd = ssthresh + 3·MSS, enter fast recovery

3. Fast Recovery

After a triple-dup-ACK loss event, TCP doesn't drop to cwnd=1 (like TCP Tahoe). Instead (TCP Reno): set ssthresh = cwnd/2, cwnd = ssthresh + 3·MSS. For each additional duplicate ACK, cwnd += 1 MSS. When a new ACK arrives (loss repaired), cwnd = ssthresh and transition to congestion avoidance.

Fairness and AIMD

Why TCP's additive-increase multiplicative-decrease converges to equal bandwidth sharing, and its limits.

AIMD — The Saw-Tooth Pattern

TCP's congestion control is called Additive Increase, Multiplicative Decrease (AIMD): increase cwnd by 1 MSS per RTT (additive); halve cwnd on a loss event (multiplicative). This produces the characteristic "saw-tooth" behavior — probing upward, crashing back, probing again.

Convergence to Fairness

Consider two TCP connections sharing a bottleneck link of capacity R. Both start at different points. AIMD provably converges to equal sharing:

AIMD Fairness Convergence — Equal Bandwidth Share Line

AIMD Fairness Proof Intuition: Starting from any point, additive increase moves the operating point along a 45° line (equal increase for both). When loss occurs (above x+y=R line), multiplicative decrease moves toward the origin along a ray. These two movements spiral toward the intersection of the equal-share and full-utilization lines — regardless of starting point.

Limits to Fairness

UDP Unfairness

UDP has no congestion control. A high-bandwidth UDP stream will not back off during congestion, crowding out TCP connections that do. This is a known unfairness problem — an active research area.

Parallel TCP Connections

An application can open multiple TCP connections. With 11 parallel connections on a 10-connection link, the app gets over R/2 bandwidth — taking an unfair share. Modern web browsers use multiple parallel connections for this very reason.

High-Speed TCP Problem: At 10 Gbps with RTT=100ms and MSS=1500B, TCP needs a loss rate of <2×10⁻¹⁰ to sustain throughput. That's essentially zero loss — existing congestion-control mechanisms break down at this scale. This motivates newer protocols (QUIC, BBR, CUBIC) designed for high-bandwidth, long-distance paths.
