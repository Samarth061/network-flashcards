Source port as return address: In UDP, the sender's source port is placed in the source port field so the receiver knows where to reply. The destination's reply reverses src↔dst port values.

Welcoming socket: A TCP server has one special socket that listens on port N. Each new accepted connection gets its own connection socket identified by the full 4-tuple. Modern servers use threads, not processes, per connection.

Key rdt3.0 insight: Sender cannot distinguish lost data, lost ACK, or delayed packet — the response is the same in all cases: retransmit. Sequence numbers handle the resulting duplicates.

SR window constraint reason: If window > seq_space/2, after wraparound the receiver cannot tell if a received packet is a retransmission of packet 0 (old) or a new packet 0 (next window). The two scenarios are indistinguishable.

TCP Sequence & Acknowledgment Numbers — Telnet Example

Client ISN=42, Server ISN=79. User types 'C' (1 byte). Three segments are exchanged:

SegmentDirectionSeqACKDataNotes
1Client → Server4279'C' (1 byte)Client waiting for byte 79 from server
2Server → Client7943'C' (echo)ACK for byte 42 + echo piggybacked on server data
3Client → Server4380(none)Pure ACK — client received byte 79 from server

Piggybacking: Segment 2 combines an acknowledgment (ACK=43) with data (echo of 'C') in one segment, saving a round trip. This is standard TCP behavior when a reply is immediately available.

TCP RTT Estimation & Timeout Interval
// Exponentially Weighted Moving Average (EWMA) — α = 0.125 EstimatedRTT = (1−α)·EstimatedRTT + α·SampleRTT = 0.875·EstimatedRTT + 0.125·SampleRTT // RTT Deviation (variability estimate) — β = 0.25 DevRTT = (1−β)·DevRTT + β·|SampleRTT − EstimatedRTT| = 0.75·DevRTT + 0.25·|SampleRTT − EstimatedRTT| // Timeout Interval (margin = 4 × standard deviation estimate) TimeoutInterval = EstimatedRTT + 4·DevRTT // Rules: // - Never measure SampleRTT for retransmitted segments (Karn's algorithm) // - On timeout: DOUBLE TimeoutInterval (exponential backoff) // - After any ACK/new-data event: recompute from formula above
TCP Reliable Transfer — Sender Logic
NextSeqNum = InitialSeqNum; SendBase = InitialSeqNum; Event: data from application create segment with seq = NextSeqNum if (timer not running): start_timer pass segment to IP NextSeqNum += length(data) Event: timer timeout retransmit segment with smallest seq number (oldest unACK'd) start_timer // restart with doubled interval Event: ACK(y) received if (y > SendBase): SendBase = y // advance window if (outstanding unACK'd): start_timer else: // duplicate ACK dupACKcount++ if (dupACKcount == 3): retransmit segment y // fast retransmit!

TCP 3-Way Handshake & Connection Teardown
StepSenderFlagsSeq / ACKAction
1 — SYNClient → ServerSYN=1seq=client_isn (random)Client requests connection; no data
2 — SYNACKServer → ClientSYN=1, ACK=1seq=server_isn, ack=client_isn+1Server allocates buffers & variables; confirms client ISN
3 — ACKClient → ServerACK=1seq=client_isn+1, ack=server_isn+1Client allocates buffers; may carry data payload
StepSegmentNotes
1 — FINCloser sends FIN=1Closer has no more data to send
2 — ACKOther side ACKsOther side may still send data
3 — FINOther side sends FIN=1When it's done sending
4 — ACKCloser sends final ACKEnters TIME_WAIT (30s–2min) before CLOSED

Why 3-way (not 2-way)? A 2-way handshake only confirms the client's SYN reached the server. The third ACK proves the server's SYNACK reached the client. Both ISNs must be mutually acknowledged for the connection to be fully synchronized.

MechanismAttacker sends thousands of SYNs, never completes handshake. Server allocates buffers for each half-open connection, exhausting memory.Server does NOT allocate state on SYN. Instead, it encodes a hash(src IP, dst IP, ports, timestamp, secret) as the ISN in the SYNACK.

AIMD Fairness — Why TCP Converges to Equal Sharing

For two connections sharing a bottleneck link of capacity R:

PhaseMovement in Throughput SpaceEffect
Additive IncreaseBoth connections increase by 1 MSS/RTT → 45° line (equal growth)Moves toward full utilization line (x+y=R)
Loss event (x+y > R)Both halve cwnd → point moves halfway toward origin along the same rayConverges toward equal-share line (y=x)
RepeatAI then MD → spirals to intersection of equal-share + full-utilizationConverges from any starting point

Fairness limits in practice: (1) Connections with shorter RTTs probe faster → unfair share. (2) An app using N parallel TCP connections gets N shares. (3) UDP flows ignore congestion → crowd out TCP.
