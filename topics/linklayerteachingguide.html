Section 1

What Is the Link Layer?

Nodes, links, frames, and the transportation analogy

Imagine sending a letter from New York to Tokyo. It travels by taxi to the airport, then by plane across the ocean, then by local courier to its destination. Each leg uses a different transport system, but together they form one end-to-end journey. Networks work exactly the same way.

A packet traveling across the Internet hops across many links — a WiFi link, then an Ethernet link, then a fiber link between routers. The link layer handles each individual hop. It doesn't care about the whole journey; it just moves data safely from one device to the immediately adjacent device.

Node: Any device running a link-layer protocol — hosts, routers, switches, WiFi access points.
Link: The communication channel connecting two adjacent nodes.
Frame: A link-layer packet — a network-layer datagram wrapped in a link-layer envelope.

Six link-layer hops from wireless host to server

Transportation Analogy

  • Tourist = Datagram
  • Transportation segment = Link
  • Transport mode (plane, train) = Link-layer protocol
  • Travel agent = Routing protocol

Two Link Types

  • Broadcast links: Many nodes share one channel (WiFi, satellite, cable). Requires coordination.
  • Point-to-point links: One sender, one receiver (long-distance fiber). Much simpler.

Datagram vs. Frame: A datagram is a network-layer (IP) packet. When it travels over a link it's wrapped inside a frame. The datagram rides as the payload of the frame. At each hop, the old frame is stripped and a new one wraps the same datagram — possibly a completely different format.

Section 2

Link Layer Services

What the link layer can do for you — and what it can't guarantee

Not all link-layer protocols provide the same services. The baseline is always the same: move a datagram from one node to the immediately adjacent node. Beyond that, services vary widely.

ServiceWhat It DoesAlways Provided?Example
FramingEncapsulates network-layer datagram into a frame with header fieldsYes — by allEthernet, 802.11
Link Access (MAC)Rules for which node can transmit on a shared broadcast linkYesCSMA/CD in Ethernet
Reliable DeliveryGuarantees delivery over each link via ACKs & retransmissionsNo — optional802.11 WiFi yes; Ethernet no
Error DetectionReceiving node detects bit errors from signal noiseUsuallyCRC in Ethernet
Error CorrectionReceiving node identifies AND fixes which bits were flippedRarelyFEC in some wireless

Why not always reliable delivery? Wired links have very low bit-error rates — adding ACK/retransmission overhead for a near-perfect wire is wasteful. TCP handles end-to-end reliability anyway. Reliable link-layer delivery matters most on high-error wireless links, where catching errors locally is faster than waiting for TCP's end-to-end timeout.

Section 3

Where Is the Link Layer Implemented?

Hardware, software, and the Network Interface Card (NIC)

The link layer is not software you write in Python. Most of it lives in dedicated hardware: the Network Interface Card (NIC), also called a network adapter. At the heart of a NIC is a special-purpose controller chip that handles framing, error detection, and link access in hardware — very fast.

NIC and host architecture — hardware/software split
1
Sending side

CPU creates a datagram and puts it in memory. NIC picks it up, wraps it in a frame, and transmits onto the physical link.

2
Receiving side

NIC receives the frame, performs CRC check, extracts the datagram, and interrupts the CPU to pass it up the stack.

3
Software component

Higher-level tasks — assembling address info, handling errors, interfacing with the network layer — run in software on the host CPU.

The link layer straddles the hardware-software boundary. Error detection runs in silicon at wire speed; address lookup and error handling run in CPU software. This split lets the link layer be simultaneously fast and flexible.

Section 4

Parity Checks

The simplest form of error detection — counting ones

Signals degrade as they travel across wires. Electromagnetic noise can flip a 0 to a 1 or vice versa. The simplest way to detect these bit errors: add an extra bit (the parity bit) so the total number of 1s is always even (even parity) or always odd (odd parity). If the receiver counts and the parity is wrong, an error occurred.

1-bit even parity — 9 ones in data → parity bit = 1 → total = 10 (even)
1
Sender counts 1s in the d data bits

Even parity: if count is odd → parity bit = 1 (to make total even). If count is even → parity bit = 0.

2
Receiver counts 1s in all d+1 bits

If total is odd (for even parity scheme) → error detected. If even → accepted.

Fatal flaw: burst errors. Single-bit parity fails to detect an even number of bit errors — two flipped bits cancel out in the count. In practice errors come in bursts (a power spike flips several adjacent bits). Single-bit parity misses about 50% of burst errors. This is why CRC is used in real link-layer implementations.

Section 5

Two-Dimensional Parity & Forward Error Correction

Not just detect — correct single-bit errors without retransmission

What if we could not only detect an error but also pinpoint exactly which bit was flipped and fix it — without asking the sender to retransmit? That's forward error correction (FEC).

Two-dimensional parity arranges the d data bits in a grid of i rows × j columns, then computes a parity bit for each row AND each column. When a bit flips, exactly one row parity and one column parity will fail. Their intersection is the corrupted bit.

2D parity — row 2 and col 2 both fail → bit (2,2) was corrupted

2D parity capabilities: Single-bit errors are detected AND corrected (row+column intersection reveals the bad bit). Two-bit errors are detected but NOT corrected (ambiguous intersection). FEC eliminates retransmission — critical for deep-space links or real-time applications where round-trip delay is enormous.

Section 6

Checksumming

Summing data bytes to catch corruption — the Internet checksum

Checksumming treats data as a sequence of numbers and sums them. The sum (or its complement) is sent alongside the data. If the receiver recomputes the sum and finds a mismatch, an error has occurred.

The Internet Checksum (TCP, UDP, IP)

1
Treat data as 16-bit integers

Break data into 16-bit chunks.

2
Sum all 16-bit integers with wraparound

Use 1's complement addition — overflow bit wraps back to the least significant bit.

3
Take the 1's complement of the sum

Flip all bits. This is the checksum placed in the header.

4
Receiver sums data + checksum

If no errors, result should be all 1s (0xFFFF). Any 0-bit indicates an error.

Why Checksums at Transport Layer?

  • Transport layer is software → needs simple, fast computation
  • Very cheap to compute in software
  • TCP/UDP use only 16-bit checksum
  • Relatively weak but fast enough

Why CRC at Link Layer?

  • Link layer runs in dedicated NIC hardware
  • Hardware does polynomial division at wire speed
  • CRC is far more powerful at detecting burst errors
  • Appropriate overhead for hardware implementation
Section 7

Cyclic Redundancy Check (CRC)

Polynomial division — the gold standard of link-layer error detection

CRC is the most powerful and widely used error detection scheme in link layers. Treat data as a giant binary polynomial and divide it by an agreed-upon generator polynomial G. The remainder R is appended to the data. If the receiver divides the received data+R by G and gets a non-zero remainder, there's an error.

All arithmetic is done in modulo-2 (no carries, no borrows). Addition = subtraction = XOR.

R = remainder of (D × 2r) ÷ G // mod-2 arithmetic D = data bits (d bits) G = generator polynomial (r+1 bits) // agreed in advance R = CRC remainder (r bits) Transmitted bits = D followed by R // d + r bits total // Receiver check: divide received (D,R) by G if remainder == 0: // no error else: // error detected — discard frame

Worked Example

D = 101110 (6 bits), G = 1001 (r = 3). Goal: find R = 3-bit CRC.

D × 2³ = 101110000. Divide by 1001 in mod-2 arithmetic. Remainder = 011. Transmitted = 101110011.

Receiver divides 101110011 by 1001 → remainder 000 → no error ✓

StandardGenerator bitsUsed InDetects all burst errors ≤
CRC-89ATM headers8 bits
CRC-1617HDLC, USB16 bits
CRC-3233Ethernet, IEEE 802.332 bits

Why XOR (mod-2) arithmetic? XOR has no carries, making it extremely simple to implement in hardware gates. The entire CRC computation is done by a chain of XOR gates and shift registers at wire speed — which is why CRC lives in hardware, not software.

Section 8

The Multiple Access Problem

When many nodes share one channel — who talks when?

Imagine a WiFi network with 30 laptops all transmitting at once. The radio waves collide in the air and nobody receives anything useful. This is the multiple access problem. A multiple access protocol coordinates who transmits when on a shared broadcast channel.

The ideal protocol for a broadcast channel of rate R with M active nodes: (1) if only 1 node is active → throughput = R bps, (2) if M active → each gets R/M bps, (3) fully decentralized — no single point of failure, (4) simple and cheap.

Three categories of multiple access protocols
Section 9

Channel Partitioning: TDM & FDM

Divide the channel into time slots or frequency bands — give each node its own lane

Time-Division Multiplexing (TDM)

Time is divided into frames, each frame divided into N time slots. Node i always transmits in slot i. No collisions — but if only 1 of N nodes is active, it still only gets R/N bps. The other N−1 slots sit idle.

TDM — 4 nodes, repeating time slots

Frequency-Division Multiplexing (FDM)

The channel is divided into N frequency bands. Each node gets its own band of R/N bps and transmits continuously on that frequency. Multiple nodes transmit simultaneously on different frequencies — no collisions. Same waste problem: 1 active node still only gets R/N bps.

The fundamental drawback of channel partitioning: If only 1 of N nodes has data, it still only gets R/N bps. The other N−1 slots/bands sit idle. This is extremely wasteful for bursty traffic.

Section 10

Code Division Multiple Access (CDMA)

Everyone talks at once — unique codes keep signals separate

CDMA assigns each node a unique code. All nodes transmit simultaneously on the same frequency, each encoding bits using its code. A receiver that knows the sender's code can decode the intended signal even with other signals present — like tuning in to a specific conversation in a noisy room because you know the "language."

Codes: Orthogonal chipping sequences — chosen so that different codes don't interfere with each other.
Anti-jamming: Spread spectrum nature makes CDMA resistant to deliberate interference — originally developed for military use.
Use today: 3G cellular networks, GPS signal separation. Detailed study in Chapter 6 (wireless).

Section 11

Slotted ALOHA

Each node rolls the dice — and waits for a clear slot

What if instead of pre-assigning slots we let any node transmit whenever it has data — but give it a random backoff after a collision? That's the ALOHA philosophy. Slotted ALOHA adds one constraint: time is divided into fixed slots, and nodes only start transmitting at slot boundaries.

1
New frame → wait for next slot start → transmit the entire frame

All nodes are synchronized to slot boundaries.

2
No collision → done!

Transmission succeeded — move on.

3
Collision detected → retransmit with probability p in each subsequent slot

Toss a coin each slot: retransmit with prob p, skip with prob (1−p). Keep trying until success.

Slotted ALOHA — collision (C), empty (E), and successful (S) slots

Efficiency Analysis

Probability a given node succeeds in a slot: p(1−p)^(N−1). Probability any node succeeds: Np(1−p)^(N−1). Setting derivative to zero: optimal p* = 1/N. As N → ∞:

max efficiency = limN→∞ N · (1/N) · (1 − 1/N)^(N−1) = 1/e ≈ 0.37

Only 37% of slots do useful work. 37% are empty. 26% are wasted on collisions.

Reality check: A 100 Mbps slotted ALOHA network delivers only ~37 Mbps aggregate throughput. The other 63% is lost to collisions and idle slots.

Section 12

Pure (Unslotted) ALOHA

Fully decentralized — transmit immediately, no synchronization needed

In pure ALOHA, when a frame arrives a node immediately transmits — no waiting for a slot boundary. No synchronization needed. But a frame is now vulnerable to collision with transmissions that started before it or during it, creating a vulnerability window of 2 frame times (vs 1 for slotted).

Maximum efficiency: 1/(2e) ≈ 0.18 — exactly half of slotted ALOHA. The price of removing synchronization.

Section 13

CSMA and CSMA/CD

Listen before speaking, stop if someone interrupts — the Ethernet way

ALOHA nodes are like rude partygoers — they talk without listening. CSMA encodes two polite human rules as network protocols:

Carrier Sense (CS)

  • "Listen before speaking"
  • Sense channel before transmitting
  • If another node is transmitting → wait
  • If idle → begin transmission

Collision Detection (CD)

  • "Stop if someone talks over you"
  • While transmitting, monitor channel
  • If foreign signal detected → abort immediately
  • Wait random time → retry

Why do collisions still happen with carrier sensing? Because of propagation delay. When node B starts transmitting, its signal takes time to reach node D. In that window D senses the channel as idle and starts transmitting — causing a collision even though both sensed first.

CSMA/CD space-time diagram — propagation delay causes collision

CSMA/CD Algorithm

1
Sense channel — if idle, start transmitting

If busy, wait until idle then transmit.

2
Monitor channel while transmitting

Watch for foreign signal energy.

3
If no collision → done!

Full frame transmitted successfully.

4
If collision detected → abort immediately

Stop transmitting. Don't waste channel finishing a damaged frame.

5
Wait random time (binary exponential backoff) → go to step 1

Random wait prevents the colliding nodes from colliding again immediately.

Efficiency = 1 / (1 + 5·d_prop / d_trans) d_prop = max propagation delay between any two adapters d_trans = time to transmit a max-size frame // As d_prop → 0: efficiency → 1 (instant collision detection) // As d_trans → ∞: efficiency → 1 (once you grab channel, hold it long)
Section 14

Binary Exponential Backoff

Wait range doubles with each collision — adapts to congestion

After the n-th collision, a node chooses K randomly from {0, 1, 2, …, 2ⁿ − 1} and waits K × 512 bit-times before sensing again. The range doubles with each successive collision — adapting to the number of competing nodes.

Collision #K chosen fromMax wait (10 Mbps)
1st{0, 1}51.2 μs
2nd{0, 1, 2, 3}153.6 μs
3rd{0 … 7}358.4 μs
4th{0 … 15}~768 μs
10th+ (capped){0 … 1023}~52 ms

Why exponential growth makes sense: Repeated collisions mean many nodes are competing. By exponentially increasing the backoff range, the algorithm adapts: few competitors → short backoff (low latency). Many competitors → long backoff (reduces collision probability). Range is capped at n=10 to prevent infinite delays.

Section 15

Taking-Turns Protocols

Polling and token-passing — orderly coordination without wasted slots

Polling Protocol

A master node cycles through all nodes in round-robin, inviting each to transmit up to N frames. No collisions. But: polling delay (time to ask inactive nodes) and a single point of failure — if the master crashes, the whole network stops. Used in Bluetooth (802.15).

Token-Passing Protocol

A small special token frame circulates among nodes in a fixed order. When you receive the token, you may transmit up to a maximum number of frames, then pass it on. No token = can't transmit. Fully decentralized — no master node.

Token passing ring — token circulates, authorizing transmission

Section 16

DOCSIS: A Multiple Access Case Study

Cable internet combines FDM, TDM, random access, and centralized allocation in one network

Cable internet (DOCSIS standard) is a real-world example combining all three multiple access approaches. Many cable modems share the cable back to a central Cable Modem Termination System (CMTS).

1
FDM: downstream and upstream on separate frequency channels

Some frequencies carry traffic from CMTS to homes (downstream); others carry traffic from homes to CMTS (upstream).

2
Downstream (CMTS → modems): no multiple access problem

Only the CMTS transmits downstream. Modems just receive (~40 Mbps per 6 MHz channel).

3
Upstream: TDM mini-slots assigned by CMTS via MAP messages

The CMTS sends MAP messages specifying which modems can transmit in which mini-slots — like a centralized TDM schedule.

4
Requesting a slot: random access

To request a mini-slot, a modem transmits during designated "request slots" using random access (with binary exponential backoff on collision).

DOCSIS hybrid: FDM (separate frequency channels) + TDM (upstream mini-slots) + Random Access (slot requests) + Centralized Allocation (CMTS grants specific slots). Collision-free data transmission, random access only for lightweight control messages.

Section 17

MAC Addresses

The permanent hardware identity of your network adapter

At the network layer, devices are identified by IP addresses. But at the link layer we need a different kind of address — one that stays fixed regardless of where you move and doesn't depend on any particular network-layer protocol. Enter the MAC address.

A MAC address is a 6-byte (48-bit) address assigned to a NIC. Written in hex: 5C-66-AB-90-75-B1. IEEE manages allocations — each manufacturer buys a 24-bit prefix and assigns the remaining 24 bits.

MAC Address

  • 48 bits → 2⁴⁸ ≈ 281 trillion addresses
  • Flat structure — no hierarchy
  • Burned into NIC hardware permanently
  • Never changes, regardless of location
  • Analogy: Social Security Number

IP Address

  • 32 bits (IPv4) or 128 bits (IPv6)
  • Hierarchical: network part + host part
  • Assigned by DHCP or administrator
  • Changes when you move to a new network
  • Analogy: Postal address

Why do we need both? LANs are designed to support any network-layer protocol (not just IP). If adapters used IP addresses, they'd be tied to IP and couldn't support other protocols. MAC addresses are "protocol-neutral," letting layers evolve independently.

The broadcast MAC address is FF-FF-FF-FF-FF-FF (all 48 bits = 1). Every adapter on the LAN accepts frames with this destination.

Switches vs. NICs: Link-layer switches do NOT have MAC addresses on their interfaces — they are transparent relay devices. Routers DO have MAC addresses on each interface (a router is an endpoint of each link, not a transparent relay).

Section 18

Address Resolution Protocol (ARP)

Translating IP addresses to MAC addresses — DNS for the link layer

You know the destination's IP (from DNS). But to build a link-layer frame you need its MAC address. That's ARP's job. ARP resolves IPs to MACs — but only within the same subnet.

ARP query (broadcast) → ARP reply (unicast)

Each node maintains an ARP table mapping IP → MAC with a TTL (typically ~20 minutes). Stale entries expire automatically.

Sending Across Subnets

When the destination is on a different subnet, you cannot ARP for it directly. Instead: ARP for the first-hop router's MAC, send the frame to the router (using router's MAC), with the IP datagram's destination still set to the final host. The router strips the frame, ARPs on the next subnet, and builds a new frame.

Is ARP link-layer or network-layer? Architecturally ambiguous — encapsulated in link-layer frames but contains IP addresses. The textbook calls it "a protocol that straddles the boundary." In practice ARP is integral to IP networking on Ethernet.

Section 19

Ethernet Frame Structure

The anatomy of the most ubiquitous frame format in networking history

Every Ethernet transmission uses the same frame format — essentially unchanged for 30+ years despite 1000x speed increases.

Ethernet frame — field-by-field breakdown
Preamble8 BFirst 7 bytes = 10101010 (wake up adapters, synchronize clock). Last byte = 10101011 (the two consecutive 1s signal "data coming now").
Destination Address6 BMAC of intended receiver. If matches adapter's MAC or FF:FF:FF:FF:FF:FF, adapter accepts the frame. Otherwise discards.
Source Address6 BMAC of sending adapter. Used by switches to learn where senders are located.
Type2 BDemultiplexes to upper-layer protocol: 0x0800 = IPv4, 0x86DD = IPv6, 0x0806 = ARP. Tells the adapter which protocol to pass the data to.
Data46–1500 BPayload (usually IP datagram). MTU = 1500 bytes. Minimum 46 bytes — if datagram < 46 bytes, padding is added.
CRC4 BCRC-32 error detection. If check fails, frame is silently dropped. No ACK — Ethernet is connectionless and unreliable.

Ethernet is connectionless and unreliable. Frames are sent without handshaking and dropped silently on CRC failure. TCP above notices missing segments and retransmits. Ethernet's deliberate simplicity is a key reason for its low cost and dominance.

Section 20

Ethernet Technologies & Evolution

From coaxial bus to 10 Gbps switched star — 30 years of dominance

Ethernet was invented by Bob Metcalfe and David Boggs at Xerox PARC in the mid-1970s. Speeds have increased 1000x, the physical medium has changed, and topology has shifted — but the frame format has barely changed.

Decoding Ethernet Names: Speed + BASE + Medium

Topological Evolution

1
1970s–early 1990s: Bus (coaxial cable)

All nodes share one coaxial cable. True broadcast — CSMA/CD required. Cable break kills the whole network.

2
Late 1990s: Hub-based star

Hosts connect to a central hub with twisted-pair. Hub is a physical-layer repeater — broadcasts every bit to all ports. Still a broadcast medium, CSMA/CD still needed.

3
2000s–present: Switch-based star

Hubs replaced by switches. Smart store-and-forward at Layer 2. No collisions. Full-duplex. CSMA/CD no longer needed. This is modern Ethernet.

Section 21

Link-Layer Switches

Self-learning, collision-free, plug-and-play — the workhorse of modern LANs

A switch receives frames, buffers them, and forwards them out only the specific interface leading toward the destination. It is transparent: hosts address frames to each other, unaware a switch is in between.

Filtering and Forwarding

Self-Learning

1
Start empty

Switch table is empty at boot. All frames are flooded.

2
Learn from incoming frames

Every frame teaches: "source MAC X came from interface Y." Record (MAC, interface, timestamp).

3
Age out stale entries

If no frame from MAC X for the aging time (e.g., 60 min), delete entry. Handles devices that leave the network.

Switch poisoning attack: An attacker floods the switch with frames having many fake source MACs. When the table fills, the switch reverts to flooding all frames — effectively becoming a hub that a sniffer can capture. Mitigated by port security features that limit MAC addresses per port.

Section 22

Virtual LANs (VLANs)

Multiple logical networks on one physical switch — isolation without rewiring

Two departments (EE and CS) share the same physical switches but don't want to see each other's broadcast traffic. VLANs solve this: the administrator assigns groups of ports to separate logical networks. Traffic from EE ports can never reach CS ports.

Single switch with two VLANs — logical traffic isolation

VLAN Trunking and 802.1Q

When multiple VLAN-enabled switches connect, a trunk port carries frames from all VLANs across a single inter-switch link. The 802.1Q standard inserts a 4-byte VLAN tag into the Ethernet frame to identify which VLAN the frame belongs to.

The VLAN tag contains: TPID (2 bytes, value 0x81-00) + Priority (3 bits) + VLAN Identifier (12 bits, supporting up to 4,096 VLANs).

VLANs solve three problems: (1) Traffic isolation — broadcasts stay within VLAN. (2) Efficient switch use — one 96-port switch can serve 10 VLANs. (3) User mobility — moving a user from EE to CS requires only a software reconfiguration, no physical rewiring.

Section 23

MPLS — Multiprotocol Label Switching

Fixed-length labels for faster forwarding and traffic engineering

MPLS blurs the line between link and network layers. Instead of performing a longest-prefix-match lookup on a 32-bit IP address at every hop, MPLS assigns a short label to each flow and forwards based on the label — much faster. Label-switched routers add a small MPLS header between the Layer-2 and Layer-3 headers.

Label20 bitsVirtual-circuit-like identifier — replaces IP longest-prefix-match lookup. Up to ~1M labels.
Exp (traffic class)3 bitsQoS/priority marking.
S (Stack bit)1 bitEnd of label stack indicator — MPLS supports stacked labels for advanced features.
TTL8 bitsTime-to-live — prevents loops.

Label-switched routers don't look at the IP destination address. They look at the incoming label, consult a simple table (label → outgoing interface + new label), swap the label, and forward. Dramatically faster than IP lookup.

MPLS traffic engineering: MPLS allows paths that IP routing alone could not create. Operators can split traffic across multiple paths (load balancing), send premium traffic on faster paths, or quickly reroute around failures using precomputed backup paths. IP always picks just one "least-cost" path. Additional uses: VPNs (isolating customer traffic within an ISP), QoS differentiation, fast failover.

Section 24

Data Center Networking

Tens of thousands of servers, hierarchical switches, and the bandwidth bottleneck

Modern cloud services (Google, Amazon, Facebook) are powered by massive data centers. Networking these servers efficiently — while controlling cost — is one of the most important networking challenges today.

1
Servers ("blades") stacked in racks

Each rack holds 20–40 servers. A Top-of-Rack (TOR) switch sits at the top. Each server connects to its TOR at 1 Gbps.

2
TOR switches connect to tier-2, then tier-1 switches

Traffic flows up the hierarchy to access routers and border routers connecting to the Internet.

3
Load balancer at the entry

External traffic enters via a border router, hits a load balancer, which distributes requests across servers and provides NAT.

The bandwidth bottleneck: The traditional hierarchical topology limits inter-rack bandwidth. Many data center applications (MapReduce, distributed training) need high bandwidth between arbitrary server pairs — they can't be confined to one rack. The solution: fully-interconnected topologies where each tier-1 switch connects to ALL tier-2 switches, providing multiple disjoint paths and multiplying aggregate bandwidth.

Traditional Hierarchical

  • Scalable to 100K+ servers
  • Simple and well-understood
  • Bottleneck at core links
  • Expensive top-tier switches

Fully-Connected

  • High aggregate bandwidth (multiple paths)
  • Any server can talk to any other at full rate
  • Uses cheaper commodity switches
  • More complex routing
Section 25

A Day in the Life of a Web Page Request

Every protocol from DHCP to HTTP — an integrated end-to-end journey

Let's watch every protocol fire as a student (Bob) boots his laptop and loads www.google.com. This integrates everything from Chapters 1 through 5.

Phase 1: Getting an IP Address (DHCP)

1
Bob's laptop sends DHCP Discover (broadcast)

UDP (port 67) → IP (src 0.0.0.0, dst 255.255.255.255) → Ethernet (dst MAC FF:FF:FF:FF:FF:FF). Nobody knows the DHCP server's MAC yet.

2
Switch floods to all ports (including router/DHCP server)

Switch has no entry for Bob yet → broadcasts. This is also how it learns Bob's MAC.

3
Router (DHCP server) responds: DHCP ACK

Assigns: Bob's IP (68.85.2.101), DNS server (68.87.71.226), default gateway (68.85.2.1), subnet mask.

Phase 2: Translating the URL (DNS + ARP)

4
ARP query for the gateway router's MAC

Bob only has the gateway's IP. Broadcasts ARP query → router replies with its MAC. Bob caches it.

5
DNS query for www.google.com

DNS query → UDP → IP (dst: DNS server) → Ethernet (dst MAC: gateway router's MAC) → router forwards via BGP/OSPF routing.

6
DNS responds with Google's IP: 64.233.169.105

Response travels back through the network to Bob.

Phase 3: TCP and HTTP

7
TCP three-way handshake with Google

SYN → SYN-ACK → ACK. Connection established on port 80.

8
HTTP GET → Google's web server

Browser sends HTTP GET → TCP segment → IP datagram → Ethernet frame → all the way to Google.

9
HTTP response → page displayed

Google sends HTML → TCP → IP → Ethernet → back to Bob. Browser renders the page. Done!

The big picture: Loading one web page used: DHCP (get IP) → ARP (get gateway MAC) → DNS (translate hostname) → TCP (reliable connection) → HTTP (actual page). Every layer participated. Every frame traversed 6+ links, each with its own link-layer protocol, while carrying the same IP datagram throughout. This is the layered architecture in action.
