Section 01

BGP Interview Summary

💬 30-Second Explanation

BGP is the routing protocol that connects the internet's autonomous systems — the independent networks run by ISPs, companies, and universities. Unlike interior routing protocols that optimize for speed, BGP is built around policy: who can send traffic where, and through which path, based on business relationships.

The 2-Minute Version

The internet is made of thousands of Autonomous Systems (ASes) — each one is a network under a single administrative control (like Google, Comcast, or your university). These ASes need a way to tell each other what IP addresses they can reach. That's BGP's job.

BGP speakers establish TCP sessions on port 179 and exchange route information. When a BGP router learns a route, it stores it, applies policy filters, runs a best-path decision algorithm, and then advertises it onward to neighbors.

The key insight: BGP doesn't find the fastest path — it finds the policy-preferred path. Operators configure which routes to prefer, which to reject, and which to advertise. This is what makes BGP the right tool for inter-domain routing where business, legal, and peering agreements matter.

The Strong Interview Answer

What Problem BGP Solves

Interior routing protocols (OSPF, IS-IS) assume a single administrative domain. The internet is many separate domains that don't trust each other. BGP provides a way for these domains to exchange reachability information while each maintaining full control over their routing policy.

Why Policy Matters

An ISP may not want to route traffic through a competitor's network. A company may refuse to carry transit traffic for others. BGP expresses these constraints via path attributes and filtering. You can prefer certain paths, deprioritize others, or block them entirely.

Why BGP Differs from OSPF/RIP

OSPF uses link-state flooding to build a full topology map and picks lowest cost. RIP counts hops. BGP carries the entire AS path and picks routes based on configurable policy rules — not just a metric. BGP also scales to the entire internet; OSPF would collapse under that load.

📌 If Asked "What is BGP?" — Say This

"BGP is the inter-domain routing protocol of the internet. It runs over TCP between routers in different Autonomous Systems, exchanges IP reachability information using path attributes, and selects routes based on operator-configured policy rather than a simple metric. It's path-vector, not link-state or distance-vector — it carries the full AS path with each route, which enables loop detection and policy-based selection."

Section 02

The Big Picture

BGP End-to-End Route Flow — from TCP session to route advertisement
🎤 Narrate This Diagram in an Interview

"Two BGP routers first establish a TCP connection on port 179. They exchange OPEN messages to agree on parameters, then confirm with KEEPALIVE. Once established, routers send UPDATE messages containing routes with path attributes. Received routes land in the Adj-RIB-In. Import policy filters them. The best-path algorithm runs on the survivors. Winners go into the Loc-RIB — the local best routes — and also get installed into the forwarding table. Then export policy runs, routes are placed in the Adj-RIB-Out, and UPDATE messages are sent to downstream peers."

Section 03

Core Mental Model

Three big ideas underlie everything in BGP. If you understand these, you can reason through any interview question.

Big Idea #1 — BGP is a Path Vector Protocol

Plain English: Every route advertisement carries the full sequence of AS numbers it has traversed. When you learn a route, you know exactly which ASes it passed through — not just the destination.

Why interviewers care: This is how BGP avoids routing loops without requiring full topology knowledge. If you see your own AS number in the AS_PATH of an incoming UPDATE, you drop it — it's a loop.

❌ Wrong Answer

"BGP uses hop count like RIP to avoid loops."

✅ Correct Version

"BGP uses the AS_PATH attribute — a list of every AS the route has crossed. If a router sees its own AS in the path, it discards the route. No loop, no topology map needed."

Big Idea #2 — BGP is About Policy, Not Shortest Path

Plain English: BGP doesn't pick the fastest route or the fewest hops. It picks the route that matches operator-defined rules — which AS relationships to prefer, which transit to avoid, what traffic to accept.

Why interviewers care: This distinguishes BGP from every IGP. The internet's routing is driven by peering agreements and business relationships, not link costs.

❌ Wrong Answer

"BGP picks the shortest AS path."

✅ Correct Version

"AS_PATH length is just one step in the decision process, and it's not even the first one. LOCAL_PREF and degree of preference come first. An operator can easily prefer a longer path through a trusted peer over a shorter one through an untrusted transit."

Big Idea #3 — BGP Separates Four Distinct Phases

Session Establishment

TCP connection, OPEN/KEEPALIVE exchange, FSM progression to Established. No routes exchanged yet.

Route Learning

UPDATEs received, routes stored in Adj-RIB-In. Raw, unfiltered.

Route Selection

Policy applied, best-path algorithm runs, winner stored in Loc-RIB and FIB.

Route Advertisement

Export policy applied, routes placed in Adj-RIB-Out, UPDATEs sent to peers.

❌ Wrong Answer

"BGP just floods route updates to all neighbors."

✅ Correct Version

"BGP has a clear pipeline: sessions first, then routes are received, filtered by import policy, best-path selected, and finally advertised outward after export policy. Each phase is independent and configurable."

Section 04

Session Lifecycle — FSM

BGP uses a six-state Finite State Machine. Knowing this helps you troubleshoot and answer "why isn't this session coming up?"

BGP FSM — Idle → Connect → Active → OpenSent → OpenConfirm → Established
IDLE

What: Initial state. BGP is waiting for a start event.

Advances when: Admin enables BGP or a "start" event fires.

Watch out: Persistent Idle = admin shutdown, or repeated TCP failures triggering backoff.

CONNECT

What: BGP is actively attempting a TCP connection to the peer.

Advances when: TCP connection succeeds → OpenSent.

Watch out: TCP fails → moves to Active. Check ACLs, routing to peer IP.

ACTIVE

What: TCP failed; BGP is retrying connections.

Advances when: A TCP connection succeeds.

Watch out: Stuck in Active = TCP unreachable. Wrong peer IP, firewall, no route.

OPEN SENT

What: TCP up, OPEN message sent, waiting for peer's OPEN.

Advances when: Peer's OPEN received and accepted.

Watch out: OPEN rejected = mismatch in AS number, hold time, BGP version, or router ID.

OPEN CONFIRM

What: Both OPENs exchanged. Waiting for KEEPALIVE to confirm.

Advances when: KEEPALIVE received from peer.

Watch out: Hold timer mismatch can stall here. Check timers on both sides.

ESTABLISHED

What: Full session up. UPDATEs, KEEPALIVEs, NOTIFICATIONs flow normally.

Watch out: Drops to Idle on NOTIFICATION or hold timer expiry. Look for policy rejections or flapping.

Section 05

Route Lifecycle

1
UPDATE Received
Peer sends an UPDATE with NLRI (prefixes) and path attributes (AS_PATH, NEXT_HOP, LOCAL_PREF, etc.)
2
Adj-RIB-In
Route is stored as-received. Unfiltered. One per peer-prefix pair.
3
Import Policy Applied
Route maps, filters, community matching, attribute modification. Routes may be accepted, rejected, or modified here.
4
Best-Path Decision Process
Among all surviving routes for a given prefix, BGP runs its decision algorithm to select one winner.
5
Loc-RIB Updated
The winner is stored in the Loc-RIB and installed in the forwarding table (FIB/kernel routing table).
6
Export Policy Applied
Before advertising to each peer, export filters run. Attributes may be changed (e.g., strip LOCAL_PREF for EBGP).
7
Adj-RIB-Out & Advertise
Route is placed in per-peer Adj-RIB-Out, and an UPDATE is sent to the peer.

Special Route Events

Route Withdrawal

A peer sends an UPDATE with a Withdrawn Routes field containing the prefix. The route is removed from Adj-RIB-In, the decision process reruns, and if the best path changes, peers are notified.

Route Rejected

Import policy drops the route, or loop detection fires (own AS in AS_PATH), or NEXT_HOP is unreachable. Route never enters best-path competition.

Route Replaced

A new UPDATE arrives with better attributes. Best-path reruns. New winner goes to Loc-RIB, old route withdrawn from Adj-RIB-Out, new route advertised.

Re-advertisement Trigger

Best path changes, export policy changes, or a ROUTE-REFRESH is requested. BGP is incremental — only changes trigger UPDATEs, not full table dumps.

⏱ 60-Second Route Processing Explanation

"A BGP UPDATE arrives carrying prefixes and attributes. The router stores it in Adj-RIB-In. Import policy runs — it can filter or modify the route. All surviving routes for a prefix compete in the best-path decision process, which checks LOCAL_PREF, AS_PATH length, NEXT_HOP reachability, and more. The winner is installed in the Loc-RIB and the forwarding table. Then export policy runs per-peer, and the route is advertised outward via Adj-RIB-Out. If the route is later withdrawn, the process reverses: route is removed, best-path reruns, and peers are notified of the change."

Deep Dive: UPDATE Message

Withdrawn Routes

List of prefixes (NLRI) that are no longer reachable via this peer. The receiver removes these from Adj-RIB-In and reruns best-path if needed.

Path Attributes

The policy knobs: AS_PATH, NEXT_HOP, LOCAL_PREF, MED, ORIGIN, COMMUNITY, etc. Apply to all NLRI in this message.

NLRI

Network Layer Reachability Information — the actual IP prefixes being advertised (e.g., 192.0.2.0/24). These are the "routes" in the routing sense.

📌 If Asked "What Does UPDATE Carry?" — Say This

"An UPDATE message has three parts: the Withdrawn Routes field (prefixes being removed), the Path Attributes field (AS_PATH, NEXT_HOP, LOCAL_PREF, etc.), and the NLRI field (the new prefixes being advertised). One UPDATE can only carry one set of path attributes, so prefixes with different attributes need separate messages."

Section 08

Path Attributes That Matter Most

AS_PATH AS Path MUST KNOW
PLAIN ENGLISHOrdered list of AS numbers the route has crossed. Prepended by each AS as the route travels outbound.
PREFERENCEShorter AS_PATH is preferred (fewer hops = simpler path). But this is not the first decision criterion.
SCOPEBoth IBGP and EBGP, but only EBGP adds its own AS on transit.
LOOP DETECTIf your own AS is in the received AS_PATH, discard the route — it looped back.
INTERVIEW TIPAS_PATH manipulation (prepending) is a common traffic engineering tool — you make a path look longer to discourage selection.
NEXT_HOP Next Hop MUST KNOW
PLAIN ENGLISHThe IP address of the next router to send packets toward this prefix. Must be reachable for the route to be usable.
EBGP RULEEBGP sets NEXT_HOP to its own IP. The peer can reach that IP directly (they're neighbors).
IBGP RULEIBGP does NOT change NEXT_HOP by default — the original EBGP NEXT_HOP is preserved. All IBGP routers must have a route to that IP via an IGP ("NEXT_HOP self" is the fix).
INTERVIEW TIP"Why isn't this route in the forwarding table?" → Check if NEXT_HOP is resolvable. This is a classic trap.
LOCAL_PREF Local Preference MUST KNOW
PLAIN ENGLISHUsed within an AS to indicate the preferred exit point for outbound traffic. Higher = preferred.
PREFERENCEHIGHER LOCAL_PREF wins. Default is 100.
SCOPEIBGP only — shared among all routers in the AS. Stripped before sending to EBGP peers.
VS MEDLOCAL_PREF controls OUTBOUND traffic (which exit path this AS uses). MED influences INBOUND traffic (which entry point a neighbor uses to reach you).
INTERVIEW TIP"Set LOCAL_PREF 200 on routes from your preferred upstream; set 100 on backup upstream. All routers in your AS will prefer the primary exit."
MED Multi-Exit Discriminator MUST KNOW
PLAIN ENGLISHA hint to a neighboring AS about which entry point is preferred when multiple connections exist between the same two ASes.
PREFERENCELOWER MED is preferred. Default is 0.
SCOPECrosses AS boundaries (sent to EBGP peer) but only affects that one neighbor. Not propagated further by default.
VS LOCAL_PREFMED = influence inbound. LOCAL_PREF = influence outbound. Very commonly confused.
INTERVIEW TIPMED is advisory — the receiving AS can ignore it. Only compared among routes from the same neighboring AS by default.
ORIGIN Origin KNOW WELL
VALUESIGP (i) = route from interior protocol. EGP (e) = route from EGP (legacy). INCOMPLETE (?) = redistributed from elsewhere.
PREFERENCEIGP > EGP > INCOMPLETE
INTERVIEW TIPOrigin matters in best-path tiebreaking but rarely drives real-world decisions. Know the order, don't over-weight it.
ATOMIC_AGGREGATE / AGGREGATOR Route Aggregation Attributes KNOW WELL
ATOMIC_AGGREGATETells downstream peers that this route was aggregated and some path information may be lost.
AGGREGATORIdentifies which router and AS performed the aggregation.
INTERVIEW TIPAggregation reduces table size (e.g., 192.168.0.0/24 + 192.168.1.0/24 → 192.168.0.0/23). ATOMIC_AGGREGATE is the warning label that specifics were lost.
⭐ The 4 Attributes You Absolutely Must Know
AS_PATH — Loop prevention + policy (shorter preferred)
NEXT_HOP — Must be reachable; IBGP doesn't change it
LOCAL_PREF — Outbound preference within AS (higher wins)
MED — Inbound hint to neighbor (lower wins, advisory)

🎤 "How Does BGP Choose the Best Path?"

"BGP runs a sequential elimination process. First it checks LOCAL_PREF — the highest wins, representing AS-wide outbound preference. Then AS_PATH length — shorter is preferred. Then ORIGIN code, then MED, then EBGP over IBGP, then IGP cost to NEXT_HOP. Remaining tiebreakers are router-ID and peer address. Policy (LOCAL_PREF) comes before metric (AS_PATH length) — that's the key insight."

🎤 "Why Doesn't BGP Use Shortest Hop Count?"

"BGP is inter-domain — it connects autonomous systems under different administrative control. An AS hop is not a uniform unit; one AS could be a small company, another could be a massive Tier-1 ISP. More importantly, the internet is governed by policy: peering agreements, transit costs, and legal constraints. A company may refuse to transit traffic for competitors regardless of hop count. BGP expresses this through configurable policy attributes, not a simple metric."

⏱ Explain IBGP vs EBGP in 45 Seconds

"EBGP is BGP between different autonomous systems — it's what connects your network to your ISP. EBGP adds your AS to the AS_PATH, sets NEXT_HOP to itself, and typically runs directly between neighbors. IBGP is BGP within a single AS — it distributes routes internally. IBGP doesn't add to AS_PATH and doesn't change NEXT_HOP by default. The critical gotcha: IBGP routes won't be re-advertised to other IBGP peers without route reflectors or a full mesh, because that would create loops."

⚠ Common Traps
  • NEXT_HOP not reachable: IBGP preserves the original NEXT_HOP. If that IP isn't in the IGP, routes won't be usable. Fix: "next-hop self".
  • IBGP full mesh: In IBGP, routes from one IBGP peer can't be re-advertised to another IBGP peer. You need either a full mesh, route reflectors, or confederations.
  • TTL assumption: EBGP defaults to TTL=1, so peers must be directly connected (or use EBGP multihop).

📌 "Why Is BGP Path Vector, Not Plain Distance Vector?"

"In distance vector, each router only knows the distance to a destination and the next hop — not the full path. BGP carries the entire AS sequence for each route. This is path vector. The difference matters: with the full path, BGP can detect loops (own AS in path), apply policy per-path, and avoid the counting-to-infinity problem that plagues distance vector protocols. You can also do traffic engineering based on which ASes a path traverses."

Why BGP Runs Over TCP

BGP sessions carry a lot of state. Routes must be delivered reliably and in order — a lost UPDATE or out-of-order message would corrupt the routing table. TCP provides this for free. OSPF and RIP handle their own reliability at the protocol level, which is simpler for small, fast intra-domain networks but wouldn't scale to BGP's needs.

Section 12

Troubleshooting and Failure Scenarios

Session Never Reaches Established

Symptom: BGP stays in IDLE, CONNECT, or ACTIVE indefinitely.

Likely Causes: TCP unreachable (routing, firewall, ACL), wrong peer IP/AS configured, port 179 blocked.

Strong Answer: "First I'd check if TCP can reach the peer — can the router ping the BGP peer IP? Is port 179 open? Then I'd verify the neighbor configuration on both sides: AS numbers, peer addresses. If stuck in ACTIVE, it's almost always a TCP-layer problem."

Session Established but KEEPALIVEs Stop / Hold Timer Expires

Symptom: BGP session drops repeatedly with NOTIFICATION error code 4 (Hold Timer Expired).

Likely Causes: CPU overload, link congestion losing keepalive packets, timer misconfiguration.

Strong Answer: "Hold timer expiry means KEEPALIVEs weren't received within the negotiated hold time (default 90s, keepalive every 30s). I'd check CPU load on both peers, look for packet loss on the link, and verify timer configurations match. Temporary fixes include increasing the hold time, but the real fix is the underlying issue."

OPEN Rejected (NOTIFICATION Sent)

Symptom: Session gets to OpenSent or OpenConfirm then immediately drops with error code 2.

Likely Causes: AS number mismatch, router-ID conflict, unsupported capability, hold time incompatibility.

Strong Answer: "Error code 2 is OPEN Message Error. The most common causes are wrong AS number configured on either end, or a duplicate router-ID in the same AS. Check the NOTIFICATION subcode — it tells you exactly what field was rejected."

Invalid or Unreachable NEXT_HOP

Symptom: Routes appear in Adj-RIB-In but not in Loc-RIB or routing table.

Likely Causes: For IBGP: NEXT_HOP is the original EBGP next-hop, not reachable via IGP. For EBGP: rare, but possible if next-hop isn't directly reachable.

Strong Answer: "In IBGP, the NEXT_HOP isn't changed by default — it stays as the EBGP speaker's address. If that IP isn't in the IGP routing table, the route is invalid and won't be installed. The fix is 'next-hop self' on the border router, or ensuring the IGP carries the EBGP next-hop address."

Route Rejected Due to AS Loop

Symptom: UPDATE received but route not installed. No error, just silently dropped.

Likely Causes: Router's own AS appears in the received AS_PATH.

Strong Answer: "BGP loop detection: if the AS_PATH contains my own AS number, I discard the route — it's already visited my AS and looped back. This is why AS_PATH is so important. You'd see the route in the UPDATE but it won't enter Adj-RIB-In as a valid route."

Unexpected Best Path Selected

Symptom: A "worse" route (longer AS_PATH, higher MED) is selected over expected one.

Likely Causes: LOCAL_PREF differs between routes; step higher in decision algorithm is driving selection.

Strong Answer: "Trace the decision algorithm step by step. LOCAL_PREF beats AS_PATH length. Check if the 'unexpected' route has a higher LOCAL_PREF set by an import policy. The decision is sequential — a route winning at step 2 (LOCAL_PREF) doesn't care about step 4 (AS_PATH length)."

Route Not Advertised to Peer

Symptom: Route is in Loc-RIB but peer doesn't receive it.

Likely Causes: Export policy filtering, IBGP split-horizon (not re-advertising IBGP learned routes to other IBGP peers), route not being the best path.

Strong Answer: "Check the Adj-RIB-Out for that peer — is the route there? If not, export policy is filtering it. If it's IBGP, remember you can't re-advertise IBGP routes to IBGP peers without route reflectors. Also verify the route is actually the best path — only best paths get advertised."

Common Interview Questions

Basic Understanding
Q1What is BGP?
SHORT: Inter-domain path-vector routing protocol of the internet, policy-driven.
BGP (Border Gateway Protocol) is the protocol that connects autonomous systems — independently operated networks — across the internet. It runs over TCP, exchanges route reachability using path attributes, and selects routes based on configurable policy, not a simple metric. It's classified as path-vector because each route carries the full sequence of AS numbers it has crossed.
Saying "BGP finds the shortest path" — it finds the policy-preferred path. Shortest path is just one optional tiebreaker.
Q2Why does BGP run over TCP?
SHORT: BGP needs reliable, ordered delivery of route updates. TCP provides this.
BGP carries routing state that must be consistent between peers. A lost UPDATE message or out-of-order delivery would corrupt the RIB. Rather than implementing its own reliability, BGP delegates this to TCP. The long-lived TCP session also enables incremental updates — BGP only sends changes, not full table dumps, every time.
Confusing "runs over TCP" with "requires direct connection" — IBGP peers are often many hops apart and reachable via IGP.
Q3What is a path vector protocol?
SHORT: Like distance vector, but carries the full path (list of ASes) instead of just distance.
Path vector is a routing paradigm where each route advertisement carries the full sequence of ASes the route has traversed — not just the destination and a metric. This enables loop detection (drop if own AS is in path), policy decisions per-path (avoid specific ASes), and avoids the counting-to-infinity problem of pure distance vector. BGP uses AS_PATH as its path vector.
Saying path vector is just "distance vector with extra info" — the structural difference (full path vs just metric) changes loop detection and policy capabilities fundamentally.
Q4Why is BGP called policy-based routing?
SHORT: Because route selection is driven by configurable operator policy, not a fixed metric.
BGP's best-path algorithm is controlled by attributes like LOCAL_PREF, MED, and community values that operators set deliberately based on business relationships. An AS may prefer a longer AS_PATH through a trusted partner over a shorter path through a competitor. This policy control is the whole point — BGP enables each AS to independently decide how to route traffic based on peering agreements, transit costs, and reliability preferences.
Thinking policy only applies to filtering — policy also controls attribute modification, preference weighting, and what gets advertised to whom.
Protocol Internals
Q5What are Adj-RIB-In, Loc-RIB, and Adj-RIB-Out?
SHORT: Three routing databases — incoming routes, local best routes, and outgoing routes.
Adj-RIB-In stores routes received from a peer before policy — the raw input. After import policy and best-path selection, winners go into Loc-RIB (the local best route per prefix, also installed in the FIB). Before advertising to a peer, export policy runs and the result is placed in Adj-RIB-Out — one per peer. Think inbox → filtered decisions → customized outbox.
Confusing Loc-RIB with the OS routing table — Loc-RIB is BGP-internal. Routes are then installed into the kernel/OS routing table, which also contains OSPF, static, and direct routes.
Q6What does a BGP UPDATE message contain?
SHORT: Three parts — withdrawn routes, path attributes, and NLRI (new prefixes).
An UPDATE can carry: (1) Withdrawn Routes — prefixes to be removed from the RIB, (2) Path Attributes — AS_PATH, NEXT_HOP, LOCAL_PREF, MED, ORIGIN, etc., and (3) NLRI — the Network Layer Reachability Information, the list of IP prefixes being advertised with those attributes. One UPDATE carries one set of path attributes. Prefixes with different attributes require separate UPDATEs.
Forgetting that an UPDATE can withdraw routes even without advertising new ones — a withdrawal-only UPDATE has no NLRI section.
Q7What happens when a route is withdrawn?
SHORT: Prefix removed from Adj-RIB-In, best-path reruns, FIB updated, peer notified.
When a WITHDRAW is received for a prefix: (1) the route is deleted from Adj-RIB-In for that peer, (2) the best-path decision process runs again for that prefix among remaining routes, (3) if the best path changes, the Loc-RIB is updated, the FIB is updated, and downstream peers receive a new UPDATE — either withdrawing the route or advertising a new best path.
Assuming withdrawal always means the route disappears — if another peer advertised the same prefix, that route may become the new best and be kept in service.
Q8What does a NOTIFICATION message mean?
SHORT: A fatal error occurred. Session terminates immediately after sending NOTIFICATION.
NOTIFICATION is BGP's error message. It carries an error code (e.g., Hold Timer Expired, OPEN Message Error, UPDATE Message Error, Cease) and optionally a subcode and data field for diagnosis. After sending a NOTIFICATION, the sender closes the TCP connection — the session goes to IDLE. It's the last message a peer ever sends before disconnecting. Common causes: hold timer expiry, malformed messages, config errors, admin shutdown.
Thinking NOTIFICATION is just a warning — it always terminates the session. No recovery path; the peers must restart the FSM.
Route Selection
Q9How does BGP select the best path?
SHORT: Sequential elimination: LOCAL_PREF → AS_PATH length → ORIGIN → MED → EBGP>IBGP → IGP cost → tiebreakers.
BGP runs a decision algorithm across all valid routes to the same prefix. It eliminates candidates step by step. First, highest LOCAL_PREF wins. Then shortest AS_PATH. Then ORIGIN (IGP > EGP > incomplete). Then lowest MED (among same-neighbor routes). Then EBGP preferred over IBGP. Then lowest IGP cost to NEXT_HOP. Finally, router-ID and peer address as tiebreakers. Policy enters at the top (LOCAL_PREF) — that's the key insight.
Starting with AS_PATH length — LOCAL_PREF comes first. An operator can always prefer a longer path by setting higher LOCAL_PREF on it.
Q10What is LOCAL_PREF vs MED?
SHORT: LOCAL_PREF = outbound (higher wins, IBGP-only). MED = inbound hint (lower wins, crosses to neighbor).
LOCAL_PREF is shared within an AS via IBGP and controls which exit the AS uses for outbound traffic. Higher value = preferred. It's stripped before sending to EBGP peers. MED is sent to a neighboring AS to influence which entry point they use for traffic coming into your AS. Lower value = preferred. MED is advisory — the receiving AS can ignore it. They control opposite traffic directions.
Confusing direction: LOCAL_PREF = outbound from your AS. MED = inbound to your AS (hint to your neighbor).
IBGP vs EBGP
Q11Difference between IBGP and EBGP?
SHORT: EBGP = between ASes. IBGP = within one AS. Key differences: AS_PATH, NEXT_HOP, and advertisement rules.
EBGP is BGP between different autonomous systems — the internet's inter-domain glue. IBGP is BGP within a single AS, used to distribute externally learned routes internally. EBGP prepends its AS to AS_PATH and sets NEXT_HOP to itself. IBGP doesn't modify AS_PATH or NEXT_HOP by default. IBGP also has the critical rule: routes learned from one IBGP peer cannot be re-advertised to another IBGP peer (requires full mesh or route reflectors).
Thinking IBGP and EBGP are entirely separate protocols — they're the same protocol, just with different behaviors depending on whether the session is intra-AS or inter-AS.
Q12Why does IBGP need a full mesh or route reflectors?
SHORT: IBGP split-horizon prevents re-advertising between IBGP peers — all peers need direct sessions to receive all routes.
BGP's loop prevention rule for IBGP: a route learned from an IBGP peer will not be re-advertised to another IBGP peer. This prevents routing loops within the AS, but means every IBGP router needs a direct session to every other IBGP router to receive all routes — O(n²) sessions. Route Reflectors break this by allowing designated routers to re-advertise IBGP routes to other IBGP peers, reducing session count.
Confusing IBGP split horizon with the RIP split horizon concept — they're both called split horizon but protect against different things in different protocols.
Troubleshooting
Q13Why is BGP slower to converge than IGPs?
SHORT: Deliberate — BGP prioritizes stability and policy correctness over speed.
BGP uses timers designed for stability: MRAI (Minimum Route Advertisement Interval, ~30s EBGP / 5s IBGP) rate-limits how fast route changes propagate. Hold timers are typically 90s. These slow convergence but prevent route flaps from destabilizing the global routing table. The internet's stability depends on BGP not overreacting to transient failures. BGPsec and modern operational practices (BFD, reduced timers) can speed it up when needed.
Calling BGP's slowness a flaw — it's intentional. Rapid convergence at internet scale would create cascade instability.
Q14Why must NEXT_HOP be resolvable?
SHORT: BGP can't forward packets without knowing how to reach the NEXT_HOP — an unresolvable NEXT_HOP means the route is unusable.
A BGP route says "to reach prefix X, send packets to NEXT_HOP Y." If the router has no route to reach Y (no IGP entry, no direct connection), it can't actually forward the packet. BGP checks NEXT_HOP reachability before installing a route in the FIB. For IBGP, this is a common issue — the NEXT_HOP is an external IP that all internal routers must reach via an IGP, or by using "next-hop self."
Thinking a route in Adj-RIB-In is automatically usable — it needs NEXT_HOP resolvability and best-path selection to reach the FIB.
Q15How does BGP avoid routing loops?
SHORT: AS_PATH inspection — if your AS is already in the path, discard the route.
BGP's primary loop prevention mechanism is AS_PATH checking: when a router receives an UPDATE, it checks if its own AS number appears in the AS_PATH. If it does, the route is discarded — it has already transited this AS and looped back. For IBGP, the split-horizon rule prevents intra-AS loops. No topology map needed — path vector carries its own loop-detection data.
Claiming BGP uses TTL for loop prevention — TTL limits hop count but isn't the BGP-level mechanism. AS_PATH is.
Design / Architecture
Q16What is an Autonomous System?
SHORT: A network under single administrative control, identified by an ASN, that participates in BGP.
An Autonomous System (AS) is a collection of IP prefixes and routers under a single administrative authority that presents a unified routing policy to the internet. Each AS has a globally unique AS Number (ASN) — 16-bit (1–65535) or 32-bit (1–4294967295). BGP is the protocol ASes use to exchange reachability with each other. Examples: Google (AS15169), Comcast (AS7922), your university might have one too.
Thinking "autonomous" means isolated — ASes connect to many other ASes. Autonomous means independently administered, not disconnected.
Q17What is AS_PATH used for beyond loop detection?
SHORT: Traffic engineering via prepending, policy decisions (avoid certain ASes), route length-based preference.
AS_PATH is used for: (1) Loop detection — drop if own AS appears. (2) Best-path preference — shorter AS_PATH preferred in step 4. (3) Traffic engineering — AS_PATH prepending artificially lengthens the path to make it less preferred by neighbors, effectively steering inbound traffic. (4) Policy — operators can filter routes that traverse specific ASes (e.g., "don't use competitor's network").
Thinking AS_PATH is only for loop prevention — it's a rich traffic engineering and policy tool in practice.
Q18What is NLRI?
SHORT: Network Layer Reachability Information — the IP prefixes being advertised in an UPDATE.
NLRI is the field in a BGP UPDATE that contains the actual IP prefixes (e.g., 10.0.0.0/8, 192.168.1.0/24) that are being announced as reachable via the attributes in that UPDATE. It's the "what" of the announcement, while the path attributes are the "how." NLRI can also appear in the Withdrawn Routes field to remove prefixes.
Confusing NLRI with path attributes — NLRI is the destination prefixes. Attributes describe the path properties. They're separate fields in the UPDATE.
Q19What is the BGP Router ID?
SHORT: A 32-bit identifier, typically the highest loopback IP, used to uniquely identify a BGP speaker and as a tiebreaker.
The BGP Router ID is a 32-bit value (formatted like an IP address) that uniquely identifies a BGP speaker. It's sent in the OPEN message and used in best-path tiebreaking (step 10 — lowest router-ID wins among otherwise equal routes). Typically it's the router's loopback IP. If two IBGP routers have the same router-ID, one will reject the other's OPEN message.
Assuming router-ID must be a routable IP — it's just a unique 32-bit identifier. It happens to look like an IP but doesn't need to be reachable.
Q20What is route reflection and why is it needed?
SHORT: Route Reflectors allow IBGP routes to be re-advertised within an AS, avoiding the O(n²) full mesh requirement.
In IBGP, routes learned from one IBGP peer cannot be re-advertised to another IBGP peer (split horizon). Without Route Reflectors, every IBGP router needs a direct session to every other — n*(n-1)/2 sessions for n routers. Route Reflectors (RRs) are designated IBGP peers that can reflect (re-advertise) routes from IBGP clients to other clients and non-clients. This reduces session count dramatically and is how large ISPs scale their IBGP topology.
Thinking RRs run on special hardware — any BGP router can be a route reflector with the right configuration. It's a logical role, not a hardware requirement.

Whiteboard / Verbal Explanation Practice

📢 Explain BGP in 1 Minute

"BGP is the Border Gateway Protocol — the routing protocol that connects the internet's autonomous systems. An AS is a network under one administrative control, like an ISP or a university. BGP runs over TCP and lets ASes exchange IP reachability information. What makes BGP unique is that it's policy-driven: instead of picking the fastest path, it picks the policy-preferred path based on attributes like LOCAL_PREF and AS_PATH. It's path-vector, so each route carries the sequence of ASes it crossed — this enables loop detection and policy-per-path decisions."

📢 Explain BGP in 3 Minutes

"The internet is made of thousands of autonomous systems — independently operated networks identified by AS numbers. BGP is how these ASes talk to each other about which IP prefixes they can reach.

BGP peers establish a TCP session on port 179. They exchange OPEN messages to agree on parameters, then KEEPALIVE to confirm. Once the session is Established, they send UPDATE messages containing prefixes and path attributes like AS_PATH, NEXT_HOP, LOCAL_PREF, and MED.

When a router receives an UPDATE, it stores the route in its Adj-RIB-In. Import policy then filters and modifies it. The best-path decision process runs — checking LOCAL_PREF first, then AS_PATH length, ORIGIN, MED, and so on. The winner goes into the Loc-RIB and the forwarding table. Export policy runs before advertising the route outward to other peers.

The key insight is that BGP is policy-driven, not metric-driven. An operator can prefer a longer path through a trusted partner over a shorter one through a competitor, simply by setting LOCAL_PREF higher. BGP also prevents loops by checking AS_PATH — if your own AS is in the path, you drop the route."

📢 Explain Best Path Selection on a Whiteboard

Draw a vertical funnel. Label each level:

  1. Step 1: LOCAL_PREF — "Who configured the highest preference?" (Higher wins)
  2. Step 2: Locally originated? — "Did we originate this route? That wins."
  3. Step 3: AS_PATH length — "Which path crossed fewer ASes?" (Shorter wins)
  4. Step 4: ORIGIN — IGP > EGP > Incomplete
  5. Step 5: MED — "Which neighbor told us to use this entry?" (Lower wins)
  6. Step 6: EBGP > IBGP — "External peer wins over internal peer."
  7. Step 7: IGP cost to NEXT_HOP — "Which exit is topologically closer?" (Lower wins)
  8. Tiebreakers: Router-ID, peer address (lowest)

"Each step eliminates candidates. You only move to the next step when there's still a tie. Policy (LOCAL_PREF) comes before metrics — that's BGP's core design philosophy."

📢 Explain IBGP vs EBGP to a Junior Engineer

"Think of BGP as having two modes. EBGP is when you're talking to a router in a completely different company's network — across an AS boundary. That's the internet-facing mode. EBGP marks the route with your AS number and sets the NEXT_HOP to itself, so the neighbor knows exactly where to send traffic.

IBGP is when you're talking to another router inside your own company's network. You're sharing routes internally. IBGP doesn't add your AS to the path — that would make it look like the route crossed an AS boundary it didn't. And IBGP doesn't change NEXT_HOP — it preserves the original value so the forwarding decision matches reality.

The tricky part: IBGP routers won't re-advertise routes to each other by default. So if you have 10 routers, they all need to talk to each other directly, or you need Route Reflectors to act as a hub."

📢 Explain How a Route Travels Through BGP

"Let's trace a route from origin to your router. An AS originates a prefix — say 1.2.3.0/24. It advertises it to its EBGP peers in an UPDATE message with AS_PATH = [originating AS], NEXT_HOP = border router IP, ORIGIN = IGP. Each peer receives this, stores it in their Adj-RIB-In, applies import policy, and if it passes, runs best-path. The winner goes into their Loc-RIB and FIB. Then they set NEXT_HOP to themselves, prepend their AS to AS_PATH, apply export policy, and send it to their EBGP peers. This repeats across the internet until the route reaches you — each hop adding one AS to the AS_PATH. When you eventually receive it, the AS_PATH tells you every AS the route crossed."

Things People Mix Up in BGP Interviews

ConfusionWhat People ThinkWhat's Actually True
RIB vs Routing Table Loc-RIB = the routing table Loc-RIB is BGP's internal best routes. The OS routing table (RIB) holds routes from all sources. FIB is what drives actual forwarding.
Route Selection vs Advertisement Best path = what gets advertised Export policy can still filter or modify what gets advertised from the Loc-RIB. These are separate steps.
NLRI vs Path Attributes NLRI includes the attributes NLRI is only the IP prefixes. Path attributes are a separate field. All NLRI in one UPDATE share the same attributes.
LOCAL_PREF vs MED Both control the same thing LOCAL_PREF controls outbound traffic (which exit your AS uses). MED influences inbound traffic (which entry a neighbor uses to reach you).
NEXT_HOP vs forwarding next hop BGP NEXT_HOP = the router you forward to BGP NEXT_HOP might not be directly reachable. The IGP finds a route to the NEXT_HOP. The actual forwarding next hop is whatever the IGP says to use to get there.
IBGP vs EBGP IBGP is a different protocol Same protocol, different mode. The distinction is whether the session crosses an AS boundary.
Loop prevention vs tiebreaking AS_PATH length preference = loop detection AS_PATH loop detection = discard if own AS present. AS_PATH length preference = shorter preferred in best-path step 4. Separate mechanisms.
Session state vs route state Session Established = routes are working Established means sessions are up. Routes may still be filtered by policy, have unresolvable NEXT_HOP, or fail best-path. Session state ≠ route state.

Section 18

Self-Test

Try answering each question before expanding the answer. Be honest with yourself.

ST1 — Your BGP session is stuck in ACTIVE for 5 minutes. What's your first diagnostic step and why?

Answer: ACTIVE means TCP is failing. First step: verify TCP-layer connectivity — can the router reach the peer IP? Try a ping or traceroute to the configured neighbor address. Check: (1) is the peer IP correct? (2) is there a route to it? (3) is port 179 blocked by an ACL or firewall? (4) is the source IP for the TCP session what the peer expects (multi-interface routers may choose the wrong source)? ACTIVE is almost always a TCP/IP problem, not a BGP configuration problem.

ST2 — A route is in your Adj-RIB-In but not in your Loc-RIB. Name 3 possible reasons.

Answer: (1) Import policy rejected it — a route map or filter dropped the route before it could compete. (2) NEXT_HOP not resolvable — if the router can't reach the NEXT_HOP IP, the route is invalid and excluded from best-path. (3) AS_PATH loop detected — the router's own AS appears in the AS_PATH, so it discards the route. Bonus: (4) Another route to the same prefix won best-path — the route is valid but wasn't selected.

ST3 — You have two paths to 8.8.0.0/16. Path A: LOCAL_PREF=200, AS_PATH=[65001,65002]. Path B: LOCAL_PREF=100, AS_PATH=[65003]. Which wins and why?

Answer: Path A wins. LOCAL_PREF is the second (or first, after Weight) step in best-path selection, and Path A has higher LOCAL_PREF (200 > 100). AS_PATH length (step 4) is only checked when LOCAL_PREF ties. Since LOCAL_PREF differs, we never even look at AS_PATH. This illustrates the core BGP insight: policy (LOCAL_PREF) overrides metric (AS_PATH length).

ST4 — You configure a route in IBGP. Peer A learns it. Will Peer B, also connected via IBGP, learn it from Peer A automatically?

Answer: No. IBGP split horizon prevents Peer A from re-advertising a route learned from another IBGP peer to Peer B. Peer B must either: (1) have a direct IBGP session to the route's originator (full mesh), or (2) be served by a Route Reflector that can forward IBGP routes to clients. This is one of the most important IBGP gotchas and is why real networks use Route Reflectors or BGP confederations.

ST5 — What does NEXT_HOP self do and when would you use it?

Answer: "next-hop self" is an IBGP configuration that makes the local router set the BGP NEXT_HOP to its own IP when advertising routes to IBGP peers, overriding the default behavior of preserving the original EBGP next-hop. You use it when IBGP peers don't have an IGP route to the original NEXT_HOP — typically on border routers that learn routes via EBGP and need to distribute them internally. Instead of requiring all internal routers to know the external EBGP IP, they just send traffic to the border router.

ST6 — What is the difference between route selection and route advertisement in BGP?

Answer: Route selection is the best-path decision process that picks one winner per prefix from all received routes — this updates the Loc-RIB. Route advertisement is the outbound process: export policy runs, and UPDATE messages are sent to peers. They're independent: a route can be selected as best but blocked by export policy from being advertised. A route can also be advertised (to some peers) but not to others, depending on per-peer export policy. "Best path selected" does not guarantee "advertised to all peers."

ST7 — How does BGP scale to the global internet but OSPF doesn't?

Answer: OSPF requires every router to have a complete map of the topology (full link-state database) and run Dijkstra's algorithm. This scales to thousands of routers, not hundreds of thousands. BGP operates at a higher abstraction: ASes, not individual routers. BGP hides internal topology entirely — you only see the AS path, not the internal structure of each AS. This allows 80,000+ ASes to participate with ~900K routes without any router needing to know the internal topology of other ASes. Policy also allows ASes to aggregate routes (fewer, larger prefixes), further reducing table size.

ST8 — A peer keeps sending NOTIFICATION error code 4. What does this mean and how do you fix it?

Answer: Error code 4 is Hold Timer Expired — your peer stopped receiving KEEPALIVEs within the hold time and terminated the session. Possible causes: (1) high CPU on either router preventing keepalive processing, (2) link congestion or packet loss dropping keepalive packets, (3) timer misconfiguration (one side negotiated lower hold time). Diagnosis: check CPU on both sides, look for packet loss on the BGP path, verify timer configuration. Short-term fix: increase hold timer. Long-term fix: address the underlying cause (CPU, link quality).

ST9 — Explain why BGP is classified as path-vector, not distance-vector, in one clear paragraph.

Answer: In distance-vector protocols like RIP, a router only knows the distance (metric) to a destination and the next-hop direction — it doesn't know the actual path. BGP carries the complete sequence of AS numbers the route has traversed (AS_PATH) with each advertisement. This transforms the protocol from "I'm this far away" to "here's every AS the route crossed to get here." This distinction enables BGP to detect loops (own AS in path = discard), make policy decisions per-path (avoid specific ASes, prefer certain transit providers), and avoid counting-to-infinity problems. The full path is the key structural difference that earns BGP the "path-vector" classification.

ST10 — Router X receives a route for 10.0.0.0/8 from both an EBGP peer and an IBGP peer, all else equal. Which wins?

Answer: The EBGP route wins. Step 7 in BGP's best-path decision prefers EBGP routes over IBGP routes, all else being equal. This reflects the design philosophy that external routes (closer to the traffic's destination, already having traversed an AS boundary) are preferred over internal redistributions of that same external information. This step is evaluated after LOCAL_PREF, local origination, AS_PATH length, ORIGIN, and MED are all tied.

The Absolute Essentials

If You Remember Only 5 Things

1. BGP is Policy, Not Shortest Path

Policy attributes (LOCAL_PREF especially) come before metrics (AS_PATH length) in every decision. The internet runs on business agreements, not hop counts.

2. AS_PATH = Loop Detection + Policy

If your AS is in the received AS_PATH, drop it (loop). Shorter AS_PATH preferred in step 4. Operators manipulate it via prepending for traffic engineering.

3. LOCAL_PREF (outbound) vs MED (inbound)

LOCAL_PREF: IBGP-only, higher wins, controls which exit your AS uses. MED: crosses to neighbor, lower wins, hints which entry point to use. These are opposite directions.

4. IBGP Doesn't Change NEXT_HOP

IBGP preserves the original EBGP NEXT_HOP. All internal routers must resolve it via IGP, or use "next-hop self" on the border router. This is the #1 IBGP gotcha.

5. Three RIBs, Three Phases

Adj-RIB-In (received raw) → Loc-RIB (local best, in FIB) → Adj-RIB-Out (per-peer outbound). Import policy between 1→2, export policy between 2→3. Selection ≠ advertisement.
